# 代码可读性

以读者能顺着代码解释业务规则为目标。先阅读调用方与数据类型，找出实际需要记忆或来回跳转的地方，再选择局部改写或提取业务函数。

## 条件与回退

- 本项目避免嵌套、连续的三元表达式，包括 JSX 中的多状态文案。两个简单值之间的选择可以保留单层三元。
- 多个互斥结果用 `if` / 提前返回或 `switch`，让优先级和默认值可见。不要换成多层 `&&` / `||`、嵌套 `??` 或立即执行函数来压缩同一组分支。
- 阈值判断按顺序展开；重复使用的判断可提取有业务名称的函数。只有一次使用且含义清楚的分支可以留在调用处，不为减少行数创建通用工具。
- 保留 `0`、空串、`null`、`undefined` 的原有区别；修改 `||` / `??` 前核实领域语义。尤其注意未知胜率、零场次和缺失排名。

配装分路的规则可表达为：

```ts
function resolveRecommendationPosition(mode: OpggMode, position: OpggPosition): OpggPosition {
  if (mode !== 'ranked') return 'none'
  if (position === 'none') return FALLBACK_OPGG_POSITION
  return position
}
```

请求参数和缓存键应复用这一规则，避免各自复制嵌套分支；不要顺便更改未知分路的回退策略。

## 数据流与命名

- 一段代码同时做解析、过滤、排序和返回结构转换时，按有意义的阶段命名。短而直观的 `filter().map()` 可保留，不按链长机械改写成循环。
- 当每项需要多步解析、多个跳过条件或临时排序信息时，考虑 `for...of`。用明确的 `{ tier, build }` 等结构保存排序信息，避免向返回对象塞入临时字段再用解构剥离。
- 在转换边界统一解析外部字符串；变量名区分外部数据、有效条目与展示数据。比较函数用 `left` / `right` 或具体领域名称，避免多层 `data`、`item`、`a`、`b` 掩盖对象含义。
- 能直接返回已有结构时，不逐字段重复重建同一个对象；先确认对象是否共享、后续是否会修改。
- `sort()` / `reverse()` 的修改应作用于明确归属当前函数的数组；共享缓存、props 和 API 结果需要保留原值时先复制。
- 用类型收窄和早期校验表达有效数据，不为使改写通过编译引入 `any`、双重断言或无依据的非空断言。

## 职责与副作用

- 提取函数应对应可命名的业务规则，例如模式识别、分路回退、胜率颜色或状态文案。相关规则就近放置，不把一次使用的细节升级为通用框架。
- 保持数据转换、宿主接口写入、React 展示的边界。优先复用项目已有规则，避免请求和缓存各自推导同一上下文。
- 异步代码需要看得出谁拥有请求、何时失效、哪里清理。重排分支时保留会话 / token 检查、同步锁和 `finally`；不得为“顺序更直观”串行化独立请求或吞掉原有错误。
- 保持副作用的执行次数和顺序，包括日志、通知、store 写入和 DOM 注入。不要在 `map` 中夹带写操作。
- 注释解释业务限制、单位、回退原因和宿主行为，不逐句复述代码。复杂阈值有现成业务命名时复用；不把每个字面量都提升成常量。

## 本仓库的审查重点

- `src/lib/build-recommendation/`：模式与分路推导是否一致，ARAM.GG 排序数据能否顺着读懂，排名回退的优先级是否明确。
- 配装面板、更新页和选人分析：状态文案与颜色是否重复推导，JSX 是否藏有多分支表达式。
- `src/lib/player-strength-score.ts`：保留角色阈值、权重与比较边界；整理表达方式不等于重新调分。
- 监听器、轮询与请求 Hook：清理逻辑和过期检查应靠近其资源，不为拆分而隐藏生命周期。

## 验证与交付

- 遵循根目录 `AGENTS.md` 的 Git、验证与安全构建约定，保留用户已有修改，不批量格式化无关文件或生成产物。
- 审查 diff 时逐项核对分支优先级、阈值、排序稳定性、默认值和副作用。可读性改写默认保持行为；发现行为错误时单独说明并验证。
- 运行适用的类型检查和现有测试；只有现有检查未覆盖重要行为边界时才补测试，不为私有辅助函数逐行复刻实现。
- 汇报具体减少了哪些重复判断或理解负担；不要用行数减少、函数数增加或技能校验通过代替可读性结论。
